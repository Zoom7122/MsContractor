# Скрипты тестовых данных МойСклад

Скрипты используют Python 3 и `requests`:

```bash
python3 -m pip install requests
```

Подключение задаётся в `scripts_for_test_data/.env.test_data`: `MS_TOKEN` либо
`MS_LOGIN` и `MS_PASSWORD`, при необходимости `MS_BASE_URL` и
`MS_REQUEST_DELAY_SECONDS` (по умолчанию `0.4`, то есть 400 мс). Переменные окружения имеют
приоритет над файлом. Токен имеет приоритет над логином и паролем.

Количество КА задаётся через `MS_COUNTERPARTY_COUNT`, а количество документов каждого
выбранного типа на один КА — через `MS_DOCUMENTS_PER_TYPE`. По умолчанию создаётся один
документ каждого типа. Например, чтобы создать по 1000 документов каждого выбранного типа
на каждый КА:

```dotenv
MS_COUNTERPARTY_COUNT=3
MS_DOCUMENTS_PER_TYPE=1000
```

Зависимые документы создаются в том же количестве: например, при выборе `salesreturn`
скрипт также добавляет `demand`, поэтому на один КА будет создано по 1000 `demand` и
`salesreturn`.

Документы, создаваемые в сценариях возвратов, задаются отдельно в `.env.test_data`:

```dotenv
MS_DOCUMENT_TYPES=salesreturn,purchasereturn
MS_SALESRETURN_DOCUMENTS=factureout,paymentout,cashout,loss
MS_PURCHASERETURN_DOCUMENTS=facturein,factureout,paymentin,cashin
```

Один тип можно указать в обоих списках — тогда он создаётся в обоих сценариях.
Для `purchasereturn` настройка `facturein` создаёт два документа: существующий
`facturein` на связанную `supply` и ещё один `facturein`, привязанный к самому
`purchasereturn`. Для второго документа скрипт использует связанную `supply` как
обязательное API-основание, затем устанавливает этот `facturein` в поле
`purchasereturn.factureIn`. Для `salesreturn` допускается
только связь через `paymentout`, поскольку прямой связи `facturein` с возвратом
покупателя в API МойСклад нет.

Если в `MS_DOCUMENT_TYPES` указан `facturein`, скрипт запускает отдельный
сценарий на каждом КА. Он создаёт документы в таком порядке:

```text
supply
 ├── facturein
 ├── paymentout (через operations)
 ├── purchasereturn (через supply)
 └── cashout (через operations)

paymentout     → facturein (через payments)
purchasereturn → supply.facturein (через purchasereturn.factureIn при создании)
cashout        → supply.facturein (через cashout.factureIn при создании)
```

Для `purchasereturn` и `cashout` используется уже созданный на `supply`
`facturein`, а ссылка передаётся сразу в POST создаваемого документа. Отдельный
PUT после создания в этом сценарии не используется: МойСклад принимает его без
ошибки, но не сохраняет связь. Вторую фактуру на тот же `supply` создавать
нельзя — API возвращает ошибку `35001`. Отдельный `paymentout` не создаётся:
один платёж создаётся на `supply` и затем используется как основание для своего
`facturein`.

## Удаление данных

`mscontractor_delete_all_data.py` удаляет **все записи перечисленных ниже типов
в аккаунте, доступном указанным credentials**, включая созданные вручную и
другими интеграциями. Ограничения по имени тестового контрагента или префиксу нет.
Перед удалением остановите создание и изменение данных в этом аккаунте
другими скриптами и интеграциями. Нужны права на просмотр и удаление всех этих типов.

Проверить количество записей без изменений в МойСклад:

```bash
python3 scripts_for_test_data/mscontractor_delete_all_data.py
```

Выполнить **безвозвратное удаление**, без дополнительного интерактивного вопроса:

```bash
python3 scripts_for_test_data/mscontractor_delete_all_data.py --execute
```

Порядок фиксирован:

1. Документы: заказы, счета, платежи и кассовые ордера, отгрузки и приёмки,
   возвраты, счета-фактуры, комиссионные отчёты, розничные документы и смены,
   предоплаты, складские и производственные документы, прайс-листы, начисления
   зарплаты и корректировки взаиморасчётов. Задачи и бонусные операции также
   удаляются на этом этапе.
2. Все контрагенты, включая архивных. Договоры удаляются следующим отдельным
   этапом: МойСклад может отклонить их удаление с `HTTP 409`, пока договоры
   используются контрагентами.
3. Договоры.
4. Техкарты и их группы, техпроцессы и этапы, партии, комплекты, модификации,
   товары, услуги и группы товаров. Архивный ассортимент также входит в очистку.

Документы проверяются с включением корзины там, где API её поддерживает.
Производственные задания читаются двумя запросами по `deleted`; группы техкарт
читаются через общий список, поскольку их endpoint не принимает фильтр `archived`.
Точные списки типов находятся в `DOCUMENT_TYPES`, `CONTRACT_TYPES` и
`ASSORTMENT_TYPES` скрипта.
Организации, сотрудники, склады, точки продаж, проекты, валюты, единицы измерения,
настройки аккаунта и прочие справочники вне этих списков остаются в МойСклад.

Перед удалением скрипт собирает все страницы списка, поэтому удаление не сдвигает
пагинацию. Зависимые записи удаляются раньше оснований; оставшиеся зависимости
повторяются в следующих проходах. По умолчанию разрешено до 10 проходов этапа;
для более глубокой вложенности можно передать `--max-passes 30`.
Переход к следующему этапу возможен только после подтверждённой пустоты предыдущих.
Если МойСклад отклоняет удаление из-за связи, которую скрипт не снимает, в отчёте
останутся ID и ответ API; более поздние этапы не запускаются.

У `emissionorder` и `retireorder` нет документированного DELETE самого документа
в [JSON API МойСклад](https://github.com/moysklad/api-remap-1.2-doc/tree/master/md/documents).
Скрипт проверяет их наличие: найденные документы блокируют этап удаления.
Ошибки прав, тарифа, неизвестного endpoint или некорректный ответ API также
не считаются пустым списком. Они требуют устранения причины и повторного запуска.
При 429, 5xx и сетевых сбоях выполняются до трёх повторов с задержкой; исчерпание
повторов останавливает работу. Ограничения тарифа не пропускаются молча.

JSON-отчёт сохраняется всегда, независимо от `MS_WRITE_REPORT_JSON`, в
`scripts_for_test_data/Logs_MS_test_data/mscontractor_cleanup_report_<run_id>.json`.
Он содержит исходные и оставшиеся количества, ID, прогресс этапов и тела ошибок
МойСклад. Прогресс сохраняется на границах этапов, при ошибках и периодически во
время удаления. После прерывания повторный запуск заново проверяет данные в МС.

Можно указать другой файл подключения и путь отчёта:

```bash
python3 scripts_for_test_data/mscontractor_delete_all_data.py --dry-run \
  --env-file /path/to/.env.test_data --report /tmp/ms-cleanup.json
```

Коды завершения: `0` — успешная инвентаризация (`planned`) или подтверждённая
очистка (`completed`); `1` — ошибка либо неполная очистка; `2` — ошибка аргументов;
`130` — остановка через Ctrl+C. Режим `--dry-run` и запуск без флагов делают только GET.
Настройки `MS_DOCUMENT_TYPES` генератора не ограничивают очистку.

Проверки без обращения к МойСклад:

```bash
python3 -m unittest discover -s scripts_for_test_data -p 'test_*.py'
```
